# DEVELOPMENT — руководство разработчика

## 1. Подготовка окружения

Требуется Docker с Compose v2, Python 3.11 или новее и Node.js 20 или новее для локального запуска инструментов вне контейнеров, Git.

```bash
cp .env.example .env
```

```bash
make up
```

Работа без Docker возможна для отдельных компонентов, но сервисы данных всегда поднимаются контейнерами: расхождение версий PostgreSQL или ClickHouse между разработчиками порождает ошибки, воспроизводимые только у одного человека.

## 2. Структура и границы

Прежде чем добавить файл, определите слой, которому он принадлежит:

| Вопрос | Ответ |
|---|---|
| Это HTTP-маршрут или схема запроса? | `backend/app/api/` или `backend/app/schemas/` |
| Это правило предметной области? | `backend/app/business/<модуль>/` |
| Это запрос к БД? | `backend/app/repositories/` |
| Это таблица? | `backend/app/models/` |
| Это обучение или инференс модели? | `ml/` |
| Это обработка входных данных? | `data_pipeline/` |
| Это отображение? | `frontend/src/` |

Правила зависимостей перечислены в [ARCHITECTURE.md](ARCHITECTURE.md#53-правила-зависимостей-внутри-backend) и проверяются в CI. Нарушение границы не проходит сборку.

Признаки нарушения, которые стоит замечать самому: `from fastapi import` внутри `business/`, вычисление процента роста очереди в React-компоненте, обращение к сессии SQLAlchemy из бизнес-сервиса, импорт `backend.app` из `ml/`.

## 3. Стандарты кода backend

| Правило | Причина |
|---|---|
| Аннотации типов обязательны для публичных функций | Контракт читается без чтения тела |
| Бизнес-сервисы не знают о FastAPI | Переносимость и тестируемость |
| Зависимости передаются явно | Подмена в тестах без патчинга |
| Pydantic-схемы отдельно для входа и выхода | Предотвращает утечку полей |
| Модели SQLAlchemy не возвращаются из API | Схема ответа явная |
| Исключения предметной области, а не HTTP-исключения в бизнес-слое | Слой не зависит от протокола |
| Запросы к БД только в репозиториях | Единая точка оптимизации |
| Область данных — явный параметр репозитория | Забыть её становится трудно |

Инструменты: форматирование и линтинг через `ruff`, проверка типов через `mypy`, проверка границ через `import-linter`, проверка безопасности через `bandit`. Все запускаются командой `make lint` и в CI.

## 4. Стандарты кода frontend

| Правило | Причина |
|---|---|
| Бизнес-логики нет в компонентах | Правила живут на сервере |
| Работа с API — через слой `services/` | Единая обработка ошибок и заголовков |
| Серверное состояние — TanStack Query | Кэш и инвалидация не пишутся вручную |
| Типы ответов API описаны явно | Расхождение контракта обнаруживается при сборке |
| Валидация форм через Zod | Совпадает по смыслу с серверной, но не заменяет её |
| Видимость по роли — эргономика, не безопасность | Ограничение доступа обеспечивает сервер |
| Дисклеймеры приходят с сервера | Смысл данных не зависит от клиента |

Правило отображения прогнозов и сценариев: значение никогда не показывается без горизонта, версии модели и ошибки. Компонент, отображающий прогноз, принимает их как обязательные свойства — тогда забыть их невозможно.

## 5. Работа с данными

Реальные выгрузки не попадают в репозиторий: расширения табличных форматов внесены в `.gitignore`. Для разработки используются синтетические наборы, структура которых соответствует контракту, а значения сгенерированы.

Правило: не подгонять код под конкретный файл выгрузки. Код пишется под контракт; файл проверяется на соответствие контракту. При расхождении меняется контракт — явным изменением с историей.

## 6. Миграции

```bash
make migration name="add_signal_confidence_flag"
```

| Правило | Причина |
|---|---|
| Одна миграция — одно смысловое изменение | Читаемая история и возможность отката |
| Откат реализован и проверен | Миграция без отката — односторонняя дверь |
| Изменение структуры и наполнение данными — разные миграции | Разный профиль риска и времени |
| Миграция просматривается перед применением | Автогенерация Alembic ошибается |
| ClickHouse — нумерованные SQL-файлы | Порядок применения фиксирован |

## 7. Ветвление и коммиты

Ветки от `main` с префиксом типа работы. Коммиты в формате Conventional Commits: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `ci`.

Требования к запросу на слияние: описание изменения и причины, прохождение тестов и линтеров, наличие тестов для изменений в бизнес-логике, обновление документации при изменении контрактов, ADR при изменении архитектурного решения.

## 8. Тестирование при разработке

```bash
make test
```

Минимальное требование: изменение в `business/` сопровождается тестом правила. Изменение в правах или области данных сопровождается тестом доступа. Подробнее — [TESTING.md](TESTING.md).

## 9. Диагностика

| Задача | Действие |
|---|---|
| Понять, что произошло с запросом | Найти `request_id` в ответе и в логах |
| Проследить фоновую часть | Тот же `request_id` передаётся в задачу Celery |
| Проверить состояние очередей | Инспекция Celery и метрики |
| Проверить запрос к ClickHouse | Журнал запросов и время выполнения |
| Проверить конфигурацию | `/api/v1/ready` и логи старта, без вывода секретов |

## 10. Добавление функциональности

Порядок, который сохраняет архитектуру целой:

1. Определить, к какому модулю относится правило.
2. Описать контракты: схема запроса, схема ответа, доменный тип.
3. Реализовать правило в бизнес-сервисе и покрыть тестом.
4. Добавить метод репозитория с явной областью данных.
5. Добавить маршрут, который только вызывает сервис.
6. Проверить права и область данных тестом.
7. Добавить тип и запрос на frontend.
8. Обновить документацию.

Обратный порядок — начать с компонента интерфейса — систематически приводит к тому, что правило оказывается в React.

## 11. Частые ошибки

| Ошибка | Последствие | Правильно |
|---|---|---|
| Расчёт показателя на frontend | Расхождение с сервером и с фоновым расчётом | Считать в бизнес-сервисе |
| Запрос без области данных | Утечка за границу видимости | Передавать scope явно |
| Тяжёлый расчёт в обработчике запроса | Таймауты под нагрузкой | Фоновая задача |
| Историческая аналитика в PostgreSQL | Деградация под объёмом | ClickHouse |
| Прогноз без метрики ошибки | Пользователь принимает оценку за факт | Обязательные поля контракта |
| Случайное разбиение временного ряда | Завышенное качество и бесполезная модель | Временное разбиение |
| Логирование объекта целиком | Возможная утечка | Логировать идентификаторы |
| Секрет в коде или файле конфигурации | Компрометация | Переменные окружения |

## 12. Команды

| Команда | Действие | Доступна с |
|---|---|---|
| `make up` / `make down` | Поднять и остановить окружение | PHASE 1 |
| `make up-devtools` | То же с портами диагностики на 127.0.0.1 | PHASE 1 |
| `make logs` / `make ps` | Логи и состояние сервисов | PHASE 1 |
| `make migrate` | Применить миграции PostgreSQL | PHASE 1 |
| `make migration name=...` | Создать миграцию | PHASE 1 |
| `make test` | Тесты backend и frontend | PHASE 1 |
| `make lint` | Линтеры, типы и границы модулей | PHASE 1 |
| `make smoke` | Сквозная проверка окружения | PHASE 1 |
| `make token` | Токен Keycloak для ручной проверки | PHASE 1 |
| `make shell-backend` | Оболочка в контейнере backend | PHASE 1 |
| `make seed` | Загрузить справочники | PHASE 2 |
| `make audit-data` | Отчёт Data Audit | PHASE 3 |

`make` не обязателен: эквивалентные команды `docker compose` перечислены в [README](../README.md#команды-разработки).
