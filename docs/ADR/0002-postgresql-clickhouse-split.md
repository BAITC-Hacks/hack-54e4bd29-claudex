# ADR-0002. Разделение PostgreSQL и ClickHouse

**Статус:** Принят
**Дата:** PHASE 0

## Контекст

Система работает с данными двух принципиально разных типов.

Первый — состояние: справочники организаций, пользователи, роли, сигналы с изменяемым статусом, действия, журнал аудита. Объём невелик, записи изменяются, нужны транзакции и связи, запросы точечные.

Второй — наблюдения во времени: очереди, направления, отказы, пролеченные случаи, прогнозы. Записи не изменяются после загрузки, объём растёт линейно со временем и числом организаций, типичный запрос сворачивает период по срезу организаций или региона.

Ключевой сценарий Situation Center — свести показатели всех организаций региона за период. В строковой СУБД это означает чтение всех столбцов всех строк диапазона, хотя нужны два-три столбца.

## Варианты

**Только PostgreSQL.** Одна СУБД, одна модель прав, одни миграции, простое развёртывание. Работает на малых объёмах. При росте истории аналитические запросы деградируют, а попытки исправить это индексами и предагрегатами приводят к раздуванию схемы. Расширение TimescaleDB частично снимает проблему, но добавляет зависимость и не даёт выигрыша колоночного хранения при агрегации по многим организациям.

**Только ClickHouse.** Отлично для аналитики, плохо для состояния: обновление записей дорого, транзакций нет, внешних ключей нет. Статус сигнала и журнал аудита в такой модели реализуются неестественно.

**Разделение по характеру данных.** Каждое хранилище применяется по назначению.

## Решение

Два хранилища с чётким правилом распределения.

PostgreSQL хранит регионы, организации и их профили, пользователей, роли, права, области данных, сигналы и их историю, инциденты, действия, сценарии и метаданные симуляций, метаданные моделей и импортов, конфигурацию, журнал аудита.

ClickHouse хранит наблюдения показателей, снимки очередей, ежедневные ряды направлений, отказов и пролеченных случаев, точки прогнозов, витрину признаков, предагрегаты по дням и регионам.

Правило разделения формулируется через характер данных, а не через объём: **изменяемое состояние со связями — в PostgreSQL, неизменяемые наблюдения во времени — в ClickHouse**. Такая формулировка не требует пересмотра при изменении объёмов.

Запрет в обе стороны: тяжёлая историческая аналитика не выполняется в PostgreSQL; изменяемое состояние не переносится в ClickHouse.

## Последствия

Становится проще: аналитические запросы по многим организациям за длительный период выполняются за приемлемое время без ухищрений. Рост истории не влияет на работу с сигналами и аудитом. Партиционирование по времени и TTL дают управление объёмом.

Становится сложнее: два хранилища вместо одного. Две системы миграций, две модели прав, два набора соединений, две точки отказа. Ссылочная целостность между хранилищами не обеспечивается СУБД — соответствие организаций проверяется конвейером до загрузки.

Чем платим: согласованность между хранилищами становится ответственностью приложения. Сигнал в PostgreSQL ссылается на метрики в ClickHouse, и эта связь не защищена внешним ключом. Компенсация — перенос `import_id` и версий контрактов по всей цепочке и проверка соответствия на этапе валидации.

Это осознанно принятая сложность, а не недосмотр: она указана в разделе спорных решений [ARCHITECTURE.md](../ARCHITECTURE.md#9-спорные-решения).

## Пересмотр

Если Data Audit покажет, что реальный объём данных невелик — единицы миллионов записей и глубина истории в один-два года, — ClickHouse становится избыточной сложностью. В этом случае разумнее оставить PostgreSQL с продуманными индексами и предагрегатами.

Решение о сохранении или отказе от ClickHouse принимается по результатам Data Audit, до начала PHASE 3.
