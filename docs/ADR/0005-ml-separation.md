# ADR-0005. Отделение ML от прикладного кода через порт

**Статус:** Принят
**Дата:** PHASE 0

> **Уточнение от PHASE 1.** [ADR-0011](0011-forecast-port-sync-and-async.md) расширяет контракт порта: `ForecastPort` объявляет и немедленные формы вызова, и формы, возвращающие описатель фоновой операции. Раздел «Инференс в воркере» ниже описывает массовый и регулярный прогноз, а не запрет на синхронный вызов.

## Контекст

ML-код и прикладной код развиваются по разным законам. Эксперименты требуют быстрой итерации, частой смены признаков и алгоритмов. Прикладной код требует стабильных контрактов и предсказуемого поведения.

При смешении возникают типичные проблемы: обучение начинает зависеть от моделей SQLAlchemy, бизнес-логика проникает в скрипты обучения, тяжёлые библиотеки попадают в образ API, а тестирование бизнес-правил требует наличия обученной модели.

Отдельно стоит вопрос интерпретации. Модель выдаёт число. Превращение числа в утверждение «риск высокий» — это бизнес-правило, а не часть модели. Если интерпретация окажется внутри ML-кода, изменение управленческих порогов потребует переобучения.

## Варианты

**ML внутри бизнес-сервисов.** Быстро на старте. Быстро становится неразделимым: бизнес-логика и признаки перемешиваются, тесты бизнес-правил требуют модели.

**ML как отдельный сервис по сети с самого начала.** Чистая граница, но преждевременная: добавляет сетевые вызовы, отдельное развёртывание и задержку там, где выигрыша пока нет.

**ML как отдельный модуль за портом внутри одного развёртывания.** Граница определена интерфейсом, вызов остаётся внутрипроцессным. Вынос в сервис возможен позже без изменения бизнес-кода.

## Решение

ML живёт в каталоге `ml/` и не импортирует `backend.app`. Взаимодействие идёт через порт, объявленный в бизнес-слое:

```
ForecastPort
  .predict(series, horizon, context) -> ForecastResult
  .explain(prediction_id) -> FeatureContribution[]
  .active_model(target) -> ModelVersion
```

Интерфейс объявлен в `business/forecasting/ports.py`, реализация — в `ml/inference/`. Направление зависимости обращено: бизнес-слой определяет контракт, ML его выполняет.

### Разделение ответственности

| Отвечает ML | Отвечает бизнес-слой |
|---|---|
| Признаки, обучение, оценка | Что считать высоким риском |
| Значение прогноза и неопределённость | Создавать ли сигнал |
| Вклад признаков (SHAP) | Как сформулировать объяснение для человека |
| Метрики качества модели | Считать ли прогноз пригодным для показа |

Граница проходит по различию между «что рассчитано» и «что это означает». Модель не знает, что такое риск перегрузки, — она знает распределение целевой переменной.

### Место интерпретации

`ExplanationService` в бизнес-слое переводит технический вывод в человекочитаемое объяснение. Сырые значения SHAP пользователю не показываются: правила подачи объяснения относятся к продукту, а не к модели, и меняются без переобучения.

### Инференс в воркере

Инференс выполняется в фоновой задаче ([ADR-0004](0004-background-workers-celery.md)), а не в HTTP-запросе. API читает сохранённый прогноз.

## Последствия

Становится проще: бизнес-правила тестируются с подставленной заглушкой порта без обучения модели. ML-эксперименты не затрагивают прикладной код. Управленческие пороги меняются без переобучения. Замена алгоритма не влияет на бизнес-слой.

Становится сложнее: контракт `ForecastResult` нужно проектировать заранее и поддерживать. Добавление поля в результат затрагивает обе стороны.

Чем платим: некоторым дублированием структур данных на границе. Бизнес-слой не использует внутренние типы ML напрямую — это цена независимости.

## Пересмотр

Вынос инференса в отдельный сервис становится оправданным, если он потребует существенно иных ресурсов, чем приложение, либо если время загрузки модели станет заметным. Благодаря порту такой вынос заменяет реализацию, а не бизнес-код.

Обратный пересмотр — слияние ML с бизнес-слоем — не предполагается: он разрушает возможность тестировать правила без модели.
