# ADR-0010. Состояние долгих операций хранится в PostgreSQL

**Статус:** Принят
**Дата:** PHASE 1
**Дополняет:** [ADR-0003](0003-redis-cache-broker-ratelimit.md) и [ADR-0004](0004-background-workers-celery.md)

## Контекст

ADR-0003 закрепил Redis как кэш, брокер задач и хранилище счётчиков частоты. ADR-0004 упомянул, что состояние операции сохраняется до постановки задачи, но не зафиксировал это как отдельное обязательное правило.

Celery предлагает собственное хранилище результатов, и им удобно пользоваться: статус задачи доступен по её идентификатору без дополнительного кода. Это приводит к тому, что состояние бизнес-операции начинает жить только в Redis.

Такое состояние ненадёжно по трём причинам. Оно имеет срок хранения и исчезает. Оно может быть вытеснено при нехватке памяти. Оно теряется при перезапуске брокера без сохранения на диск. Кроме того, статус задачи Celery описывает судьбу задачи, а не судьбу операции: задача может завершиться успешно, оставив бизнес-операцию в наполовину обработанном состоянии.

Для импорта данных и симуляций это неприемлемо. Пользователь должен видеть, что произошло с его импортом, спустя сутки и после перезапуска инфраструктуры.

## Решение

Состояние долгих бизнес-операций хранится в PostgreSQL. Хранилище результатов Celery используется только для технической судьбы задачи и не является источником истины.

### Общий жизненный цикл

```
PENDING → RUNNING → COMPLETED
                  → FAILED
```

| Статус | Смысл |
|---|---|
| `PENDING` | Операция зарегистрирована, задача поставлена в очередь |
| `RUNNING` | Воркер начал обработку |
| `COMPLETED` | Обработка завершена успешно |
| `FAILED` | Обработка прервана, причина сохранена |

### Обязательные правила

**Запись создаётся до постановки задачи.** Порядок: транзакция создаёт запись со статусом `PENDING`, транзакция фиксируется, и только затем задача попадает в очередь. Обратный порядок допускает ситуацию, когда воркер начинает обработку раньше, чем существует запись о ней.

**Воркер обновляет состояние транзакционно.** Переход в `RUNNING` при старте, переход в `COMPLETED` или `FAILED` при завершении — каждый в отдельной зафиксированной транзакции. Состояние, обновлённое только в памяти процесса, теряется при его аварийном завершении.

**Отказ фиксируется как состояние, а не только как исключение.** Задача, завершившаяся ошибкой, обязана записать `FAILED` с кратким описанием причины. Операция, оставшаяся в `RUNNING` навсегда, — это дефект.

**Краткое описание ошибки не содержит внутренних деталей.** Трассировка остаётся в журнале, связанном по `request_id`. В поле операции попадает причина, понятная пользователю.

**Потерянная задача остаётся видимой.** Если задача исчезла из очереди, запись сохраняет статус `PENDING` и может быть перезапущена. Это прямое следствие принятой в ADR-0003 платы за хранение очереди в памяти.

### Применение

Правило распространяется на импорт данных, расчёт симуляций, обучение и массовый инференс, формирование экспортов. Оно не распространяется на быстрые технические задачи, не имеющие самостоятельного бизнес-смысла.

## Идемпотентность импорта данных

Импорт выделен отдельно, поскольку его повторение опаснее: незамеченное дублирование искажает все построенные на данных показатели.

Минимальный состав записи импорта:

| Поле | Назначение |
|---|---|
| `id` | Идентификатор операции |
| `dataset_type` | Тип набора данных |
| `source` | Система-источник |
| `file_name` | Имя исходного файла |
| `file_hash` | Контрольная сумма содержимого |
| `status` | Статус из общего жизненного цикла |
| `created_at` | Момент регистрации |
| `started_at` | Момент начала обработки |
| `completed_at` | Момент завершения |
| `error_summary` | Краткая причина отказа |

Контрольная сумма вычисляется по содержимому файла, а не по его имени. Переименованный файл с тем же содержимым — это тот же файл.

**Повторная загрузка обнаруживается.** Совпадение контрольной суммы и типа набора с ранее завершённым импортом распознаётся до начала обработки, и пользователь получает явный ответ о том, что эти данные уже загружены.

**Молчаливое дублирование в ClickHouse недопустимо.** ClickHouse не обеспечивает уникальность средствами СУБД, поэтому защита строится на стороне конвейера.

**Конкретная стратегия дедупликации определяется после Data Audit.** Выбор зависит от того, чем являются данные: событиями с устойчивым идентификатором, снимками состояния или агрегатами. Для событий подходит ключ дедупликации, для снимков — замена раздела за период, для агрегатов — движок со схлопыванием по ключу. Выбирать стратегию до знания гранулярности данных означает угадывать.

До принятия решения действует страховка: загрузка данных за период, уже покрытый завершённым импортом, требует явного подтверждения оператора.

## Последствия

Становится проще: пользователь видит судьбу своей операции независимо от состояния Redis. Перезапуск инфраструктуры не теряет историю. Диагностика опирается на устойчивые данные.

Становится сложнее: каждая долгая операция требует записи в PostgreSQL и её аккуратного обновления. Это дополнительный код в каждой такой задаче.

Чем платим: дополнительной записью в операционную БД на каждый переход состояния. Объём незначителен — долгих операций немного по определению.

## Пересмотр

Решение не подлежит пересмотру в сторону хранения бизнес-состояния только в брокере. Возможное развитие — выделение общей таблицы операций в специализированные таблицы по типам, если состав полей начнёт существенно различаться.
