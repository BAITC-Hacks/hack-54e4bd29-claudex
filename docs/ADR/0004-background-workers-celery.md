# ADR-0004. Celery для фоновой обработки

**Статус:** Принят
**Дата:** PHASE 0

> **Уточнения от PHASE 1.** [ADR-0010](0010-persistent-operation-state.md) делает обязательным хранение состояния долгих операций в PostgreSQL с транзакционным обновлением воркером. [ADR-0011](0011-forecast-port-sync-and-async.md) снимает прочтение «инференс всегда фоновый» как архитектурный запрет: единичный быстрый прогноз может выполняться синхронно, если укладывается в бюджет времени ответа.

## Контекст

Часть операций принципиально не укладывается в бюджет HTTP-запроса: разбор и загрузка выгрузки, пересчёт агрегатов за период, обучение модели, ежедневный инференс по всем организациям, прогон Signal Engine, расчёт сценария симуляции, формирование экспорта.

Выполнение их внутри запроса даёт таймауты, удержание соединений с БД, невозможность повтора при сбое и блокировку рабочих процессов приложения. Кроме того, регулярные операции — ежедневный прогноз и прогон правил — должны запускаться по расписанию, а не по действию пользователя.

## Варианты

**Синхронное выполнение.** Проще всего, но неприемлемо: импорт выгрузки за год не завершится за время запроса, а пользователь не должен ждать.

**Фоновые задачи внутри процесса приложения.** Через средства асинхронного выполнения самого веб-фреймворка. Не требует инфраструктуры, но задача живёт в памяти процесса: перезапуск приложения теряет её, повтор не поддерживается, наблюдаемость отсутствует, масштабирование невозможно.

**Celery.** Зрелое решение с расписанием, повторами, разделением очередей и наблюдаемостью. Плата — дополнительный компонент и брокер.

**Более лёгкие очереди задач.** Проще в настройке, но уступают в зрелости расписания и наблюдаемости.

## Решение

Celery с Redis в качестве брокера на MVP ([ADR-0003](0003-redis-cache-broker-ratelimit.md)). Celery Beat для регулярных задач.

Единый поток обработки:

```
API → постановка задачи → очередь → воркер → бизнес-сервис → хранилище → результат
```

### Обязательные правила

**Задача не содержит бизнес-логики.** Она получает контекст, вызывает тот же бизнес-сервис, что и API, и сохраняет результат. Это исключает расхождение правил между синхронным и фоновым путями — классический источник ошибок, при котором импорт через интерфейс и через фон дают разный результат.

**Задачи идемпотентны.** Повторное выполнение при сбое не должно дублировать данные или искажать состояние. Для импорта ключ идемпотентности — контрольная сумма файла и период.

**Состояние операции сохраняется до постановки задачи.** Запись со статусом `PENDING` создаётся в PostgreSQL раньше, чем задача попадает в очередь. Потерянная задача остаётся видимой и перезапускаемой.

**Очереди разделены по типу нагрузки.** Обучение модели не должно блокировать быстрые операции:

| Очередь | Задачи |
|---|---|
| `default` | Быстрые операции |
| `ingestion` | Импорт и загрузка данных |
| `ml` | Обучение и инференс |
| `simulation` | Расчёт сценариев |

**Beat запускается в одном экземпляре.** Иначе регулярные задачи дублируются.

**Задачи ограничены по времени.** Мягкий и жёсткий пределы предотвращают бесконечное выполнение.

**`request_id` передаётся в задачу.** Позволяет проследить операцию от HTTP-запроса до фонового результата.

**Образ воркера совпадает с образом API.** Гарантирует идентичность бизнес-кода.

## Последствия

Становится проще: API отвечает быстро, тяжёлые операции масштабируются добавлением воркеров независимо от приложения, регулярные расчёты выполняются по расписанию, сбои приводят к повтору, а не к потере.

Становится сложнее: асинхронный поток требует отслеживания статуса на стороне клиента. Пользователь получает `202 Accepted` и идентификатор, а не результат. Интерфейс должен корректно показывать промежуточные состояния.

Чем платим: два дополнительных процесса в развёртывании и необходимость мониторинга очередей. Длина очереди и число отказавших задач становятся эксплуатационными показателями.

## Пересмотр

При устойчивой потере задач — переход на брокер с долговременным хранением. При появлении сложных зависимостей между шагами обработки — рассмотрение оркестратора конвейеров данных вместо самостоятельной композиции задач. Второе становится актуальным, если конвейер импорта вырастет за пределы линейной последовательности.
