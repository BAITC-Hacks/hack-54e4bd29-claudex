# ADR-0009. Keycloak и OIDC как единственный механизм аутентификации

**Статус:** Принят
**Дата:** PHASE 1
**Заменяет:** решение об аутентификации из [ADR-0006](0006-security-architecture.md). Остальные решения ADR-0006 — модель области данных, разделение прав и области, ответ `404` вместо `403`, неизменяемость аудита — остаются в силе.

## Контекст

ADR-0006 допускал на MVP локальный провайдер JWT с контрактом, совместимым с OIDC, чтобы не тратить время на развёртывание Keycloak в начале работы.

Практика показывает, что такая «временная» реализация несёт непропорциональный риск. Собственная аутентификация означает хранение паролей, реализацию их хеширования и смены, выпуск и отзыв токенов, защиту от перебора, восстановление доступа. Каждый из этих элементов — отдельная поверхность атаки в системе, работающей с данными здравоохранения. Ошибка в любом из них обесценивает всю остальную работу по безопасности.

Дополнительно: временная схема аутентификации почти никогда не остаётся временной. Её замена откладывается, потому что она работает.

## Решение

Аутентификация выполняется исключительно внешним провайдером OIDC. Для MVP это Keycloak.

```
Браузер → Keycloak (вход) → Frontend (получает токен)
        → FastAPI (Bearer-токен) → проверка подписи → SecurityContext
```

### Ответственность backend

Backend **не аутентифицирует пользователя**. Он проверяет предъявленный токен и строит контекст:

| Шаг | Содержание |
|---|---|
| Проверка подписи | По ключам провайдера, полученным из JWKS и закэшированным |
| Проверка claim'ов | Издатель, аудитория, срок действия, время выпуска |
| Извлечение личности | Идентификатор субъекта, имя, адрес почты |
| Разрешение ролей | Из claim'ов токена в роли системы |
| Построение контекста | `SecurityContext` с идентификатором, ролями и областью данных |
| Применение области | В бизнес-слое, по правилам ADR-0006 |

### Что MedSignal не хранит и не делает

Пароли пользователей, их хеши, процедуры смены и восстановления пароля, выпуск и обновление токенов, управление сессиями провайдера. Всё это остаётся в Keycloak.

Локальная таблица пользователей сохраняется только как проекция: идентификатор субъекта из провайдера, отображаемое имя и назначенная область данных. Она не содержит учётных данных.

### Раздельные адреса провайдера

Токен, выпущенный Keycloak, содержит издателя в том виде, в каком его видит браузер. Backend внутри сети контейнеров обращается к тому же Keycloak по внутреннему имени. Поэтому конфигурация разделена:

| Параметр | Назначение |
|---|---|
| `OIDC_ISSUER` | Публичный издатель. Сверяется с claim `iss` |
| `OIDC_INTERNAL_BASE_URL` | Внутренний адрес для получения ключей и метаданных |

Смешение этих двух адресов — типичная ошибка, дающая либо неработающую проверку, либо принятие токена с чужим издателем.

### Область данных не берётся из токена

Роли приходят из провайдера. Область данных разрешается на стороне MedSignal по собственной таблице, как установлено ADR-0006. Причина прежняя: изменение области администратором должно действовать немедленно, а не после перевыпуска токена.

### Аутентификация в тестах

Для автоматических тестов допускается подставной адаптер аутентификации, реализующий тот же интерфейс, что и проверка токена Keycloak. Он существует для того, чтобы тесты бизнес-правил не требовали работающего провайдера.

Обязательные ограничения адаптера:

| Ограничение | Реализация |
|---|---|
| Включается только явно | Отдельная переменная окружения, по умолчанию выключена |
| Невозможен вне тестовой среды | Приложение отказывается стартовать при включённом адаптере и непустой рабочей среде |
| Не является запасным вариантом | При недоступности Keycloak запросы отклоняются, а не проходят через адаптер |

Третий пункт существен: адаптер, срабатывающий при отказе провайдера, превращается в обход аутентификации.

## Последствия

Становится проще: исчезает целый класс уязвимостей, связанных с хранением паролей. Появляется готовая основа для единого входа, многофакторной аутентификации и федерации, если они понадобятся. Управление пользователями выносится за пределы прикладного кода.

Становится сложнее: Keycloak становится обязательной зависимостью среды разработки. Локальный запуск требует его старта и импорта конфигурации области. Недоступность провайдера делает вход невозможным.

Чем платим: временем старта окружения и одним дополнительным контейнером. Это принятая цена за отказ от собственной аутентификации.

## Пересмотр

Замена Keycloak на другого провайдера OIDC не затрагивает прикладной код: проверка построена на стандартных механизмах обнаружения конфигурации и наборе ключей, а не на особенностях конкретного продукта. Пересмотр потребуется только при отказе от OIDC как стандарта, что не предвидится.
