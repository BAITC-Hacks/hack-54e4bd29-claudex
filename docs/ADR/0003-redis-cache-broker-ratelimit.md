# ADR-0003. Redis для кэша, брокера и ограничения частоты

**Статус:** Принят
**Дата:** PHASE 0

> **Дополнение от PHASE 1.** [ADR-0010](0010-persistent-operation-state.md) запрещает использовать Redis как единственный источник состояния бизнес-операций. Состояние импортов, симуляций и прочих долгих операций хранится в PostgreSQL; хранилище результатов Celery описывает только техническую судьбу задачи.

## Контекст

Три потребности возникают независимо друг от друга.

Кэширование: сводка Situation Center собирается из агрегатов ClickHouse и пересчитывается при каждом открытии дашборда, хотя данные обновляются раз в сутки. Справочники организаций читаются при каждом запросе для разрешения области данных.

Брокер сообщений: тяжёлые операции выносятся в фон ([ADR-0004](0004-background-workers-celery.md)), для чего нужна очередь задач.

Ограничение частоты запросов: счётчики должны быть общими для всех экземпляров приложения, иначе при трёх экземплярах фактический лимит утраивается.

Общее требование ко всем трём: состояние не должно жить в памяти процесса, иначе приложение перестаёт быть stateless и теряет способность масштабироваться горизонтально.

## Варианты

**Три разных решения.** Кэш в памяти процесса, RabbitMQ как брокер, счётчики в PostgreSQL. Каждое решение оптимально для своей задачи. Но кэш в памяти ломает масштабирование, счётчики в PostgreSQL создают нагрузку записи на операционную БД при каждом запросе, а отдельный брокер добавляет компонент в инфраструктуру.

**Redis для всех трёх задач.** Один компонент покрывает все потребности: структуры данных с истечением срока, атомарные счётчики, списки для очередей. Плата — общая точка отказа.

**PostgreSQL как очередь.** Соблазнительно исключить компонент. Работает на малых нагрузках, но требует аккуратной реализации блокировок и создаёт нагрузку на операционную БД.

## Решение

Redis для всех трёх задач с обязательным разделением по логическим базам:

| База | Назначение | Политика |
|---|---|---|
| `REDIS_DB_CACHE` | Кэш агрегатов и справочников | Вытеснение по давности, TTL обязателен |
| `REDIS_DB_BROKER` | Очередь задач Celery | Вытеснение запрещено |
| `REDIS_DB_RESULT` | Результаты задач | TTL |
| `REDIS_DB_RATELIMIT` | Счётчики частоты | Короткий TTL |

Разделение принципиально: кэш допускает вытеснение при нехватке памяти, а очередь задач — нет. Вытеснение записи из очереди означает потерянный импорт. Разные базы позволяют разные политики и упрощают диагностику.

## Последствия

Становится проще: горизонтальное масштабирование приложения без потери кэша и без искажения лимитов. Один компонент вместо трёх в инфраструктуре. Общее состояние координации доступно всем экземплярам.

Становится сложнее: Redis становится критической зависимостью. Его недоступность останавливает постановку фоновых задач.

Обязательные меры устойчивости: кэш деградирует мягко — при недоступности Redis приложение обращается напрямую к источнику, а не отказывает; ограничение частоты при недоступности Redis работает в разрешающем или запрещающем режиме согласно явно заданной политике; недоступность брокера приводит к отказу постановки задачи с понятной ошибкой, а не к молчаливой потере.

Чем платим: Redis хранит очередь задач в памяти. При аварийной остановке без сохранения на диск незавершённые задачи теряются. Компенсация — идемпотентность задач и сохранение состояния операции в PostgreSQL до постановки в очередь: запись `DataImport` со статусом `PENDING` создаётся раньше задачи, поэтому потерянный импорт виден и может быть перезапущен.

## Пересмотр

Если потеря задач станет повторяющейся проблемой в эксплуатации, брокер заменяется на решение с долговременным хранением сообщений. Кэш и счётчики при этом остаются в Redis — разделение по логическим базам делает такую замену локальной.
