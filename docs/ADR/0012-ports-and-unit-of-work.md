# ADR-0012. Порты репозиториев и единица работы

**Статус:** Принят
**Дата:** PHASE 2
**Уточняет:** [ADR-0001](0001-modular-monolith.md) и [ADR-0010](0010-persistent-operation-state.md)

## Контекст

PHASE 1 содержал один бизнес-сервис, и он обращался к хранилищу напрямую: получал фабрику сессий SQLAlchemy и сам создавал репозиторий. Для одного сервиса это было незаметно.

С появлением предметной области выяснились три проблемы.

**Бизнес-слой начал зависеть от ORM.** Сервис импортировал `Session`, то есть правила предметной области знали, чем именно реализовано хранение. Автоматическая проверка границ это подтвердила: контракт «бизнес-слой не импортирует SQLAlchemy» оказался нарушен существующим кодом.

**Правила стало трудно проверять.** Тест бизнес-правила требовал работающей базы. Проверка «закрытый сигнал не возвращается в начальное состояние» не имеет отношения к PostgreSQL, но без него не выполнялась.

**Появилось требование атомарности.** Бизнес-операция и запись аудита должны фиксироваться вместе. Журнал, расходящийся с данными, хуже отсутствующего журнала. Без общей транзакции каждый репозиторий фиксировал бы своё.

## Варианты

**Оставить как есть.** Сервисы создают репозитории и управляют сессией. Меньше кода, но все три проблемы сохраняются, а граница между правилами и хранением перестаёт существовать.

**Абстрактные базовые классы репозиториев.** Реализации наследуются от интерфейсов, объявленных в бизнес-слое. Работает, но требует, чтобы слой репозиториев импортировал бизнес-слой — то есть обращает направление зависимости, запрещённое слоевым контрактом.

**Структурные протоколы плюс единица работы.** Бизнес-слой объявляет, что ему нужно; реализации соответствуют по форме, не импортируя объявления.

## Решение

**Порты объявлены в бизнес-слое.** `app/business/ports.py` описывает, что сервисам нужно от хранилища: методы, параметры, типы результата. Область данных входит в сигнатуру каждого запроса явным параметром.

**Протоколы структурные.** Реализации в `app/repositories/` не импортируют `ports.py`. Соответствие проверяется по форме, поэтому правило «репозитории не импортируют бизнес-слой» остаётся в силе, а подмена в тестах не требует наследования.

**Единица работы объединяет репозитории общей транзакцией.** Сервис открывает её, выполняет операцию и фиксирует явным вызовом. Выход из блока без фиксации откатывает транзакцию: забытый commit должен терять изменение, а не записывать его случайно.

**Композиционный корень собирает приложение.** `app/composition.py` соединяет сервисы с конкретными реализациями. Это единственное место, знающее обе стороны; слой API получает готовые сервисы и не создаёт их сам.

**Общие значения запроса вынесены из обоих слоёв.** Пагинация и фильтры нужны и правилам, и запросам, поэтому живут в `app/shared/`. Иначе репозиторий импортировал бы бизнес-слой ради описания фильтра.

```
API → Business Service → Port (протокол) ← Repository → PostgreSQL
                ↑                              ↑
         объявляет контракт            выполняет контракт
                        Composition root связывает
```

## Последствия

Становится проще: правила проверяются подменой хранилища в памяти, без базы. Бизнес-операция и запись аудита фиксируются вместе без дополнительных усилий. Граница между правилами и хранением проверяется машинно и не размывается.

Становится сложнее: появился отдельный файл контрактов, который нужно поддерживать вместе с реализациями. Добавление метода репозитория затрагивает два места.

Чем платим: подмена хранилища в тестах повторяет поведение настоящих репозиториев, включая фильтрацию по области данных и условное обновление по версии. Расхождение между подменой и реальностью даёт тесты, проходящие при сломанном коде. Это компенсируется тем, что те же правила проверяются и на уровне API, и не заменяет интеграционных проверок на реальной базе.

## Пересмотр

Если состав портов начнёт меняться чаще, чем правила, это признак того, что контракты описывают не потребность бизнес-слоя, а устройство таблиц. Тогда порты следует укрупнить до операций предметной области.

Возврат к прямому обращению из сервисов не предполагается: он одновременно разрушает проверяемость правил и атомарность аудита.
