# ADR-0006. Архитектура безопасности и модель доступа

**Статус:** Принят, решение об аутентификации заменено
**Дата:** PHASE 0

> **Изменение от PHASE 1.** Решение «аутентификация на MVP — локальный JWT с контрактом OIDC» отменено и заменено на [ADR-0009](0009-keycloak-oidc-authentication.md): аутентификация выполняется исключительно Keycloak по OIDC, MedSignal не хранит пароли. Все прочие решения настоящего ADR — область данных в бизнес-слое, разделение прав и области, ответ `404` вместо `403`, неизменяемость аудита, отказ старта при небезопасной конфигурации — остаются в силе.

## Контекст

Система работает с операционными данными медицинских организаций региона. Разные пользователи должны видеть разные подмножества: региональный аналитик — свой регион, руководитель организации — свою организацию. Нарушение этой границы означает раскрытие данных.

Помимо ограничения видимости требуется разделение прав на операции: аналитик исследует ситуацию, но управленческое решение фиксирует руководитель.

Целевая схема аутентификации — OIDC с Keycloak. Разворачивать и настраивать его на первой неделе MVP означает отложить всю остальную работу.

## Варианты

### Место применения области данных

**В контроллере.** Фильтр добавляется в обработчике маршрута. Проблема: фоновые задачи вызывают бизнес-сервисы напрямую, минуя контроллер, и остаются без ограничения. Кроме того, ограничение приходится повторять в каждом обработчике, и однажды его забывают.

**В репозитории неявно.** Репозиторий сам подмешивает условие из глобального контекста. Скрытая зависимость: поведение запроса зависит от невидимого в сигнатуре состояния. Тесты становятся хрупкими, а ошибка проявляется как «почему-то пустой список».

**В бизнес-слое явно.** Сервис получает `SecurityContext` и передаёт область данных в репозиторий явным параметром. Единая точка для синхронного и фонового пути, видимая в сигнатуре зависимость.

### Аутентификация на MVP

**Сразу Keycloak.** Правильная цель, дорогое начало.

**Локальный JWT без совместимости с OIDC.** Быстро, но переход позже потребует переделки бизнес-кода.

**Локальный JWT с контрактом OIDC.** Те же claim'ы, та же проверка подписи, срока, издателя и аудитории. Переключение — переменной окружения.

## Решение

**Область данных применяется в бизнес-слое явным параметром.** `SecurityContext` разрешается один раз при аутентификации и передаётся вниз. Репозиторий принимает область данных аргументом и не догадывается о ней. Вызов репозитория для данных, привязанных к организации, без области данных считается ошибкой.

**Права на операцию и область данных разделены.** Право проверяется до вызова сервиса — это свойство роли. Область данных проверяется внутри сервиса, где известен объект. Это два разных вопроса, и они решаются в двух разных местах.

**Область данных не берётся из токена.** Она разрешается на сервере по таблице `user_data_scopes` при каждом запросе. Изменение области администратором действует немедленно, а не после истечения токена.

**Объект вне области данных даёт `404`, а не `403`.** Ответ `403` подтверждает существование объекта и позволяет перебором выяснить состав организаций региона.

**Аутентификация на MVP — локальный JWT с контрактом OIDC.** Поле `external_subject` присутствует в модели пользователя с самого начала, поэтому переход на Keycloak не требует миграции.

**Приложение отказывается стартовать при небезопасной конфигурации.** Отладочный режим вне локальной среды, значения-заглушки из `.env.example`, полностью открытый CORS — каждое приводит к отказу запуска.

**Журнал аудита неизменяем на уровне прав БД.** Прикладная роль имеет право только на вставку. Это техническая гарантия, а не соглашение между разработчиками.

**Хранилища не публикуются наружу.** Публичен только обратный прокси.

## Последствия

Становится проще: изоляция данных проверяется одним типом теста, применимым к каждому читающему эндпоинту. Переход на Keycloak — изменение конфигурации. Небезопасное развёртывание обнаруживается при старте, а не в эксплуатации.

Становится сложнее: сигнатуры методов репозитория содержат дополнительный параметр. Это намеренно — забыть явный аргумент труднее, чем неявный контекст.

Чем платим: ответ `404` вместо `403` затрудняет диагностику для самого пользователя. Он не отличит «объекта нет» от «объект вне моей области». Компенсация — точная запись причины в журнале и `request_id` в ответе, по которому администратор восстановит картину.

## Пересмотр

Переход на OIDC выполняется при появлении требования единого входа либо при выходе в пилот — что наступит раньше. Модель области данных при этом не меняется: она остаётся серверной и не переносится в claim'ы токена.

Расширение модели прав до атрибутного доступа рассматривается, если появятся правила вида «видеть организации определённого профиля независимо от региона». Текущая модель со строками области данных покрывает и такие случаи явным перечислением.
