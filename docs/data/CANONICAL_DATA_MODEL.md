# MedSignal — каноническая аналитическая модель

Документ описывает реализованную модель. Предложение, из которого она
выросла, — в [CANONICAL_DATA_MODEL_PROPOSAL.md](CANONICAL_DATA_MODEL_PROPOSAL.md);
здесь зафиксировано то, что действительно создано, и чем реализация
отличается от предложения.

## 1. Что создано

| Таблица | Зерно | Источник |
|---|---|---|
| `fact_referral_events` | одно направление | ИС БГ |
| `fact_waiting_events` | одна запись очереди в срезе | ИС БГ |
| `fact_refusal_events` | один отказ | ИС БГ |
| `fact_treated_snapshot` | одна организация в одной поставке | ЭРСБ |
| `agg_referrals_daily` | организация и день | производная |
| `agg_refusals_daily` | организация и день | производная |

Измерений `dim_region` и `dim_hospital` в ClickHouse нет. Справочники
организаций и регионов живут в PostgreSQL вместе с сопоставлением, потому
что сопоставление меняется и требует решения человека, а не является
неизменным наблюдением.

## 2. Двойное хранение идентификатора организации

Каждая таблица фактов хранит организацию дважды:

| Столбец | Что это | Может отсутствовать |
|---|---|---|
| `*_org_key` или `hospital_source` | нормализованное значение из источника | нет |
| `*_hospital_id` | организация справочника | да |

Причина в результате Data Audit: выгрузки распадаются на две группы по
идентификатору организации, и общего кода между ними нет. Пока
сопоставление не подтверждено, канонический идентификатор пуст, а
исходный есть всегда — на нём и построен порядок сортировки.

Сортировать по столбцу, который пуст у части строк, нельзя.

## 3. Отличия от предложения

| Предложение | Реализовано | Почему |
|---|---|---|
| `fact_queue_snapshot` с историей срезов | `fact_waiting_events` с одной датой среза | В данных один срез, а не история |
| Наименование диагноза как измерение | только код МКБ-10 | Читаемый диагноз на уровне записи — данные о здоровье |
| Сведения об операции | только признак наличия | Для размера очереди вмешательство не нужно |
| `dim_hospital` в ClickHouse | справочник в PostgreSQL | Сопоставление изменяемо |

## 4. Происхождение записи

Каждая строка витрины несёт три столбца происхождения:

| Столбец | Что позволяет |
|---|---|
| `import_id` | найти запись об импорте в PostgreSQL |
| `source_file_hash` | опознать исходный файл по содержимому |
| `source_system` | понять, из какой системы пришли данные |

Этого достаточно, чтобы по строке витрины дойти до файла, не раскрывая
ни одного идентификатора пациента. Подробно — в [DATA_LINEAGE.md](DATA_LINEAGE.md).

## 5. Семантика времени

| Таблица | Ось | Что это |
|---|---|---|
| `fact_referral_events` | `registration_dt` | момент регистрации направления |
| `fact_waiting_events` | `registration_dt` | момент постановки в очередь |
| `fact_refusal_events` | `refuse_dt` | момент отказа |
| `fact_treated_snapshot` | `snapshot_load_dt` | **момент выгрузки, не отчётный период** |

Последняя строка — не оговорка. Отчётного периода в выгрузке пролеченных
случаев нет, и восстановить его неоткуда. Имя столбца выбрано так, чтобы
принять его за отчётный период было трудно.

## 6. Что в модели отсутствует

- Коечный фонд. В выгрузках его нет, и загрузка стационара не вычисляется.
- Возраст и любые сведения о пациенте.
- Вакцинации и онкология. К задаче о нагрузке стационаров не относятся.
