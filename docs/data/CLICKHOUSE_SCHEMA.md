# MedSignal — схема аналитического хранилища

Описывает применённые схемы. Предложение, из которого они выросли, —
в [CLICKHOUSE_DESIGN_PROPOSAL.md](CLICKHOUSE_DESIGN_PROPOSAL.md).

## 1. Версионирование

Alembic для ClickHouse не используется: он рассчитан на транзакционный
DDL, которого здесь нет. Вместо этого — пронумерованные файлы
в `database/clickhouse/migrations/` и таблица применённых версий
`schema_migrations`.

```bash
make clickhouse-migrate
make clickhouse-status
```

Свойства механизма:

- **Версия — полное имя файла.** Не числовой префикс: префикс задаёт лишь
  порядок, а полное имя не сталкивается с записями скриптов прежних фаз.
- **Изменённая после применения миграция отвергается.** Принятую миграцию
  правят новой, а не на месте.
- **Удаляющие команды запрещены.** Файл с `DROP TABLE`, `TRUNCATE` или
  `DELETE FROM` отклоняется до отправки в базу. Потеря аналитических
  данных должна быть осознанным действием человека.
- **Разбор SQL учитывает строковые литералы.** Комментарий к столбцу может
  содержать точку с запятой, и наивное разбиение рвало бы команду пополам.

## 2. Таблицы фактов

| Таблица | Движок | PARTITION BY | ORDER BY |
|---|---|---|---|
| `fact_referral_events` | MergeTree | `toYYYYMM(registration_dt)` | `(receiving_org_key, registration_dt, event_key)` |
| `fact_waiting_events` | MergeTree | `toYYYYMM(registration_dt)` | `(hospital_source, registration_dt, patient_key)` |
| `fact_refusal_events` | MergeTree | `toYYYYMM(refuse_dt)` | `(hospital_source, refuse_dt)` |
| `fact_treated_snapshot` | MergeTree | `toYYYYMM(snapshot_load_dt)` | `(hospital_source, snapshot_load_dt)` |

Выбор объясняется так:

**MergeTree, а не ReplacingMergeTree.** Замещающий движок легко принять
за механизм идемпотентности, но он ею не является: он схлопывает строки
по ключу когда-нибудь, а не в момент вставки. Идемпотентность обеспечивает
запись об импорте в PostgreSQL, и подменять её поведением движка значит
получить две разные гарантии, ни одна из которых не проверяема.

**Разбиение по месяцу события.** Запросы витрины всегда ограничены
периодом. Трёхмесячная история даёт три раздела на набор — немного, но
разбиение выбирается под будущий объём, а не под текущий.

**Сортировка начинается с организации.** Основной вопрос интерфейса —
«что происходит в этой организации». Первым столбцом стоит исходный
идентификатор, а не сопоставленный: сопоставленный пуст у части строк.

**`LowCardinality(String)` для справочных значений.** Организаций около
пяти тысяч, регионов два десятка, профилей сотня. Словарное кодирование
здесь уменьшает и объём, и время чтения.

**`Nullable(UUID)` для сопоставленных идентификаторов.** Пусто означает
«сопоставление не подтверждено». Эти столбцы не входят в ключ сортировки.

## 3. Промежуточные таблицы

Каждой таблице фактов соответствует `stg_*` с тем же составом столбцов,
разбитая по `import_id`.

Разбиение выбрано ради отката: `DROP PARTITION` удаляет ровно свой импорт
мгновенно и не трогает чужие, тогда как `DELETE` был бы отложенной
мутацией. Подробно о семантике публикации — в [IMPORT_RECOVERY.md](IMPORT_RECOVERY.md).

## 4. Агрегаты

| Таблица | Движок | Наполняется |
|---|---|---|
| `agg_referrals_daily` | SummingMergeTree | `mv_referrals_daily` |
| `agg_refusals_daily` | SummingMergeTree | `mv_refusals_daily` |

Агрегатов ровно два, и каждый отвечает на вопрос, который интерфейс
задаёт постоянно. Умозрительные разрезы «на будущее» не заводятся:
неиспользуемое представление всё равно пересчитывается при каждой
вставке и молча расходится со смыслом, когда меняется таблица фактов.

Агрегаты построены на исходном идентификаторе организации. Сопоставление
появится позже и изменится задним числом; агрегат, зависящий от него,
пришлось бы пересчитывать целиком.

Представления наполняются при вставке в таблицу фактов. Поэтому загрузка
обязана идти через публикацию из промежуточной таблицы: вставка мимо неё
оставила бы агрегаты пустыми.

## 5. Чего в схеме нет

- Идентификаторов пациентов в любом виде.
- Читаемых наименований диагнозов.
- Возраста.
- Таблиц вакцинации и онкологии.
