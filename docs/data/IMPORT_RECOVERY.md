# MedSignal — восстановление после сбоя импорта

## 1. Почему нужна отдельная процедура

ClickHouse и PostgreSQL не образуют одной транзакции. Состояние импорта
живёт в PostgreSQL, данные — в ClickHouse, и между ними возможно
расхождение, если процесс прервался посередине.

Поэтому «загружено» и «опубликовано» разведены явно, а не подразумеваются.

## 2. Порядок шагов

```
1. запись об импорте        RUNNING, фиксируется отдельной транзакцией
2. разбор и проверки
3. запись пакетов           промежуточная таблица, раздел по import_id
4. сверка числа строк       промежуточная таблица против принятых
5. публикация               перенос в таблицу фактов
6. сверка числа строк       таблица фактов против промежуточной
7. очистка промежуточной
8. отчёт о качестве,
   счётчики, состояние      COMPLETED — одной транзакцией PostgreSQL
```

Запись об импорте создаётся до начала разбора. Иначе упавший процесс
не оставил бы следа, и отличить «импорт не запускался» от «импорт упал»
было бы невозможно.

Состояние `COMPLETED` ставится только после шага 6. Импорт, дошедший
до пятого шага и прерванный, завершённым не считается.

## 3. Что происходит при сбое

Конвейер откатывает всё, что успел записать:

| Что | Как |
|---|---|
| Промежуточные строки | `DROP PARTITION` по `import_id` — мгновенно и точно |
| Опубликованные строки | `DELETE WHERE import_id = ...` — раздел содержит и чужие импорты |

Затем запись об импорте переводится в `FAILED` с краткой причиной.
Причина содержит тип ошибки и её текст, но не трассировку и не содержимое
строк: сообщение об ошибке — не место для медицинских данных. Полная
картина остаётся в журнале, связанном по `request_id`.

Если сам откат не удался, это записывается в причину отдельно: импорт
остаётся `FAILED`, но требует ручного вмешательства.

## 4. Если процесс убит

Запись останется в состоянии `RUNNING`, а в ClickHouse могут лежать
строки этого импорта. Такое состояние устраняется командой:

```bash
make data-recover IMPORT_ID=<uuid>
```

Команда удаляет строки импорта из обеих таблиц и переводит запись
в `FAILED`. После этого файл можно загрузить заново: ключ идемпотентности
переиспользует ту же запись, и дубликата не возникнет.

Завершённый успешно импорт команда не трогает. Удаление опубликованных
данных — осознанное действие, а не порядок восстановления.

## 5. Повторный запуск безопасен

Загрузка уже загруженного файла определяется по паре «тип набора и
контрольная сумма содержимого» и пропускается с исходом
`SKIP_IDEMPOTENT`. Файл не читается повторно, число строк в витрине
не меняется.

Переименованный файл — тот же файл. Файл с прежним именем и другим
содержимым — другой файл.

## 6. Диагностика

| Вопрос | Где смотреть |
|---|---|
| Что происходило | `GET /api/v1/data-imports` |
| Почему упало | `error_summary` записи об импорте |
| Что не так с данными | `GET /api/v1/data-imports/{id}/quality` |
| Какие строки отклонены | `quarantine_batches` и объект в карантине |
| Сходятся ли числа | `rows_read`, `rows_rejected`, `rows_loaded` |
| Есть ли остатки в витрине | `SELECT count() FROM <таблица> WHERE import_id = ...` |

## 7. Проверено на практике

Процедура выполнена на живом стенде: импорт переведён в `RUNNING`, как
после убитого процесса, затем восстановлен. Команда удалила ровно три
строки этого импорта и не тронула 767 130 строк соседних.
