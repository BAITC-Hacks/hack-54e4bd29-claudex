# MedSignal — дизайн доведения до проверяемого пилота

Статус: предложение к плану реализации от 23.09.2026; продуктовый код не изменён.
Основание: запрос пользователя составить план по результатам ревью проекта.
Исходный commit: ab620bc. Это новое предложение, а не изменение принятых ADR.

## Цель и граница результата

Получить один защищённый пользовательский сценарий: подтверждённые поставки →
аналитика → проверенный прогноз потока → объяснимый сигнал → действие человека →
аудит и контроль. Существующая описательная аналитика остаётся полезной даже при
отрицательном результате ML-эксперимента.

Успех разработки означает воспроизводимость, корректность и контролируемый доступ.
Успех ML означает выполнение заранее согласованной политики качества на новом
нетронутом периоде. Один результат не подменяет другой.

## Исходные факты

- Основной API: Keycloak/OIDC, RBAC/scopes, PostgreSQL, ClickHouse, Redis, Celery.
- Local pilot: pilot/api.py и ml/monitoring.py; отдельный localhost Compose,
  историческое воспроизведение и собственный JSON состояния.
- Зафиксированные объёмы принятого импорта: referrals 767130, waiting 765182,
  refusals 1508732, treated 2196. Это историческое evidence, не текущий runtime count.
- Q1 2025 не подтверждает сезонность; waiting — один срез; treated — без периода.
- 5029 несопоставленных aliases организаций и 42 aliases регионов по прежней проверке.
- В local pilot: precision 42,86%, recall 4,05%, WAPE 84,286% на двух тестовых неделях.
- Основной Phase 5A выбрал weekly_naive; локальный пилот исследует другую модель.
- Phase 8 acceptance от 18.09.2026 относится к другому baseline commit. TLS,
  corporate SSO и production E2E нельзя считать выполненными по этому отчёту.
- Последний локальный lint прошёл; typecheck блокирован отсутствующим leaflet в
  node_modules, Vitest — filesystem permissions; Docker daemon недоступен в sandbox.
  Эти ограничения окружения сами по себе не доказывают дефект исходного кода.

## Рассмотренные подходы

| Подход | Выигрыш | Ограничение |
|---|---|---|
| A. Последовательное укрепление существующего продукта | Сохраняет проверенные права, аудит, pipeline и workflow; независимые небольшие поставки | Требует явных границ между исследованием и допуском модели |
| B. Сделать local pilot основным продуктом | Быстрее демонстрировать новую модель | Повторная реализация scopes, audit, persistence, recovery; две версии правил |
| C. Сначала расширять ML и число моделей | Больше экспериментов | Не исправляет недостаток данных, качество предупреждений и интеграцию |

Предлагается A. Новые микросервисы, Kubernetes, LLM/API и прогноз освобождения
конкретной койки не нужны для этой цели.

## Четыре независимо проверяемые части

1. Воспроизводимость: чистые зависимости, CI обоих режимов, актуальные claims.
2. Поставки и mappings: явная семантика поставки, контроль полноты и пересечений,
   подтверждённые mappings и версионированное применение к уже загруженным фактам.
3. Оценка модели: замороженный протокол, новые данные, leakage tests, качество
   прогнозов отдельно от качества эпизодов предупреждений, решение о допуске.
4. Интеграция и эксплуатация: подключение допустимой модели через существующие
   порты, основной Signal/Incident/Audit, производительность, внешние production
   controls и проверяемый shadow pilot.

## Обязательные ограничения

- SOURCE DIRECTORY = READ ONLY.
- Нет исходных медицинских записей, секретов, токенов или raw identifiers в Git,
  CI, отчётах и application logs; тесты используют synthetic fixtures.
- Нет собственного JWT/password auth; основной пользовательский путь через Keycloak.
- API → Business Service → Repository Interface → Infrastructure; ML не принимает
  решения о правах, статусах инцидента и сохранении аудита.
- PostgreSQL — источник истины статусов; Redis — cache/broker/transport.
- Принятые migrations 0001–0006 и ClickHouse 001–005 не переписывать. Любые новые
  revisions строить от фактического head в момент исполнения, не резервировать номер.
- Нет destructive Git operations, удаления текущих volumes или inplace source edits.
- Нет fuzzy/fake mappings; source identity не эквивалентна canonical Hospital.
- GLOBAL сигналы доступны только соответствующим global scopes. HOSPITAL сигналы
  допустимы только после подтверждения mappings и отдельной проверки области доступа.
- Unmapped source-level model outputs остаются исследовательскими результатами;
  не превращать их в GLOBAL сигналы с фиктивной больницей.
- STALE forecast не создаёт operational FORECAST_INFLOW_GROWTH; validity и freshness
  являются разными характеристиками. Исторический анализ явно помечается.
- Пороги 20% / 35% / 50% и 72h/168h сохраняются как текущая версия политики.
  Изменение требует отдельной версии и обоснованного решения, не подгонки под test.
- Восемь reference windows spike rules строго предшествуют evaluation window,
  не пересекаются, используют только полные дни.
- DATA_QUALITY_DEGRADED требует формализованного denominator. 104644 конфликтов
  сами по себе не доказывают деградацию новой поставки.
- Scenario остаётся immutable, synchronous и не меняет автоматически Signal/Incident.
- Нет заявлений о точном прогнозе перегрузки, освобождении коек или клинических решениях.

## Поставки данных и справочники

Запросить у владельца: официальные справочники с областью кодов и периодом действия,
семантику delta/snapshot/correction, отчётный период treated, значение snapshot_dt,
периодичность, таймзону, признак завершённости поставки и независимые контрольные суммы.
Желательна более длинная история направлений и ежедневные реальные queue snapshots.
Нужны новые данные после уже просмотренного тестового периода; фиксированное число
месяцев само по себе не гарантирует достаточности эпизодов.

До получения договора поставки неизвестный день не заполняется нулём автоматически.
Файл с новым hash не обязательно содержит новые события. Пересекающиеся выгрузки
не публикуются автоматически, если owner-approved правила reconciliation отсутствуют.

Для maps предлагается версия справочника в PostgreSQL и его минимальная проекция
в ClickHouse: identity_space + normalized source key + approved canonical ID.
Версия становится доступной запросам только после проверки проекции. Запрос фиксирует
одну версию, cache key включает её. Старые facts не переписываются только ради mapping.
Публикация и отзыв mapping обязаны менять эффективную область доступа; при отсутствии
подтверждённой проекции scoped-запрос завершается безопасно, а не расширяет scope.
Это новое существенное решение, поэтому до кода нужен ADR на проекцию и публикацию.

## Допуск ML

Выделить понятную цель: обнаружение измеримого роста направлений по подтверждённой
организации, не перегрузка. В отчёте отдельно считать MAE/WAPE, precision/recall,
TP/FP/FN/TN, lead time, число alerts на организацию-неделю и интервалы неопределённости.
Повторные дни одной ситуации считать одним episode по замороженному правилу.

Train/validation/test разделены по времени. Outcome каждого training origin полностью
заканчивается до validation; аналогично validation не использует test labels.
Гиперпараметры, пороги и допустимый alert budget выбираются без просмотра test.
Региональная/организационная eligibility определяется только по прошлому.

Численные release-пороги precision, recall, false-alert budget и минимум независимых
эпизодов утверждаются владельцем процесса до финального test. Пока политики нет,
решение — POLICY_NOT_APPROVED. Недостаток новых данных — INSUFFICIENT_DATA.
Ни один из этих исходов не разрешает operational model alerts.

## Интеграция

ML adapter получает агрегаты из принятого analytics path, не читает raw CSV в HTTP.
Forecast/ModelVersion/SystemOperation используются повторно; артефакты только из
доверенного object storage с проверкой hash и версии. Сигналы сохраняются существующим
движком с provenance и dedup policy. Статусы меняются существующим workflow.
JSON replay-state.json никогда не становится production persistence.

## Приёмка

Технические gates независимы: чистая сборка; миграции; source privacy; корректность
поставок; scopes/cache; ML eligibility; workflow; latency; restore; production perimeter.
Статусы: PASS / FAIL / NOT TESTED / EXTERNAL DEPENDENCY / NOT APPLICABLE.
Для production controls шаблон или документ не является PASS.

20 concurrent users — начальный инженерный benchmark. Сохранять dataset sizes,
watermark, cache state, requests, errors, p50/p95/p99 и параметры машины. RPO/RTO,
период shadow pilot и модельные пороги — решения владельцев, не вымышленные SLA.

## Что можно начать без внешних данных

CI, восстановление окружения, документирование claims, contracts на synthetic данных,
tests утечек, версионирование mappings, evaluation harness, закрытая интеграция под
feature flag, профилирование на существующих facts и повторная проверка восстановления.
Активация актуальных прогнозов и operational hospital alerts ждёт прохождения gates.
