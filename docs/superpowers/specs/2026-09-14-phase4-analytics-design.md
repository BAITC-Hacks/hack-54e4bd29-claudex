# PHASE 4 Analytics & Situation Center — Design

## Цель и граница

PHASE 4 добавляет описательную аналитику поверх опубликованных фактов Phase 3B.
Поток остаётся слоистым: FastAPI вызывает `AnalyticsService`, сервис работает
через порт аналитического репозитория, SQL и ClickHouse остаются в реализации
репозитория. Ни прогнозов, ни risk score, ни сигналов, ни рекомендаций в этом
этапе нет.

## Идентичность организации

Аналитика различает два пространства идентификаторов:

- `canonical:<hospital_uuid>` — утверждённая организация PostgreSQL;
- `source:<sha256>` — непрозрачная ссылка на значение источника.

Хэш source-ссылки строится из `identity_space` и нормализованного значения.
`identity_space` включает источник, набор и роль поля, например
`IS_BG:REFERRALS:RECEIVING`. Это не позволяет молча объединить названия и коды
из несовместимых наборов. Исходное значение не помещается в URL. В ответе оно
может использоваться как `display_name`, поскольку является идентификатором
организации, а не пациента.

Несопоставленные организации доступны только `ADMIN` и
`HEALTH_AUTHORITY`. Остальные роли получают исключительно записи с
`canonical_hospital_id`, попадающим в разрешённый hospital/region scope.

## Метрики и семантика времени

Формулы задаются один раз в реестре метрик. Dashboard показывает:

- число направлений по `registration_dt`;
- число записей поставленного среза очереди;
- число отказов по `refuse_dt`;
- число представленных организаций без межпространственного объединения;
- число представленных региональных значений;
- актуальность и качество каждой поставки.

Временные ряды существуют только для направлений и отказов. Очередь
представляется срезом: возраст записи равен `snapshot_dt - registration_dt`.
Наблюдаемое ожидание рассчитывается только для завершённых госпитализаций с
`hospitalization_dt >= registration_dt`; некорректная хронология исключается
и возвращается отдельным счётчиком. Пролеченные случаи показываются только как
предоставленный срез, без временного ряда.

Статус направления определяется детерминированно: наличие `refusal_dt` даёт
`REFUSED`; иначе корректная `hospitalization_dt` даёт `HOSPITALIZED`; отсутствие
обеих дат даёт `WAITING`; противоречивая хронология даёт `UNKNOWN` и quality
warning. Общая доля отказов не рассчитывается, пока не доказано совпадение
числителя и знаменателя.

## API и запросы

API использует фиксированные endpoint и enum-параметры. Максимальный диапазон
дат задаётся `ANALYTICS_MAX_DATE_RANGE_DAYS` (по умолчанию 366), размер страницы
организаций ограничен общим максимумом 100. Каждый ответ содержит период,
гранулярность, источники, время генерации, watermark последнего завершённого
импорта и ограничения интерпретации.

ClickHouse возвращает агрегаты. Event-level строки через analytics API не
выдаются. Ошибки ClickHouse преобразуются в общий безопасный контракт без SQL.

## Кэш

Redis используется как необязательный ускоритель. Ключ содержит endpoint,
нормализованные фильтры, fingerprint SecurityContext scope и watermark
последних завершённых импортов. TTL короткий и настраиваемый. Отказ Redis не
ломает аналитический запрос; кэш не является источником истины.

## Privacy и качество

Для чувствительных разрезов действует подавление малых групп с порогом
`ANALYTICS_MIN_CELL_SIZE=10`. Ответ сообщает `suppressed=true` и не возвращает
точное значение. Quality-блок использует только агрегированные результаты
импорта, без исходных значений. Ни один endpoint не выдаёт patient key,
event key, код госпитализации или номер пациента.

## Frontend

`/dashboard` — Ситуационный центр с KPI, фактическими временными рядами,
возрастом текущей очереди, таблицей организаций и блоками качества/актуальности.
`/hospitals/[id]` показывает canonical hospital; `/organizations/[ref]` —
source-level организацию с явным статусом mapping. Графики ECharts имеют
текстовое резюме и табличное представление. Loading, empty, partial, suppressed
и error состояния являются отдельными компонентами.

## Проверка

Unit-тесты фиксируют формулы, границы времени, suppression, scope и cache key.
API-тесты фиксируют валидацию и авторизацию. ClickHouse integration-тесты
сверяют сумму временного ряда с числом фактов. Frontend-тесты проверяют
loading/success/empty/partial/error/suppressed. Финальная проверка выполняется
на текущих опубликованных данных без вывода строк уровня пациента.
