## Что сделано

Прогноз количества отделён от детектора роста. Детектор действительно обучается на недельных целевых метках из реальной истории. Признаки: недельные объёмы и их отношения, последние дни, вариативность, доля нулей, тенденция, день недели, объём и доля выходных. Все признаки вычисляются только из доступной истории. История диагнозов, последующая госпитализация и другие будущие исходы не используются.

Проверены 7 самостоятельных классификаторов: обычная и сбалансированная логистическая регрессия, четыре настройки градиентного бустинга, ExtraTrees. Дополнительно проверены ансамбль и пороги по группам объёма — всего 9 вариантов детектора. Численный прогноз: 3 варианта, включая исходный.

Протокол зафиксирован в MODEL_EXPERIMENT_PROTOCOL.md до экспериментов. Выбор по максимальному F2 на валидации при precision ≥40% и доле тревог ≤25%. Выбран сбалансированный HistGradientBoostingClassifier с 15 листьями и порогами по объёму организации. Группы определены по обучению: small <10, medium 10–50, large ≥50 направлений/день. Пороги: 0,750 / 0,675 / 0,075 соответственно. Score не калиброван как вероятность. Пороги нестабильны на короткой истории, особенно в небольших группах.

На валидации выбранный детектор: precision 42,31%, recall 7,17%, 52 тревоги. На повторном тесте ограничение precision уже не выдерживается — это явно показано. Кандидаты после просмотра теста не перенастраивались.

Численный прогноз выбран отдельно по MAE валидации: бустинг с absolute-error loss. Итоговый артефакт содержит обе обученные модели. Runtime рассчитывает риск и количество отдельно. Карточка не утверждает обязательный рост только потому, что классификатор сработал. Приоритет предварительный, без заявления о доказанной опасности для пациентов.

## Данные и валидация

Аудит всех 767130 строк: точных дубликатов 0; повторяющихся кодов случаев 1969; отсутствующих hospital_mo/registration_dt 0; присутствуют все 90 дат. Planned_dt отсутствует в 33704 строках, bed_profile в 372316 — они не используются текущей моделью. 1385 исходных названий превращаются в 1384 после удаления крайних пробелов; не производится неявное объединение по похожести названий. Дни с падениями и скачками не удаляются. Сведения о полноте поставки отсутствуют: отсутствие записи может означать и нулевой поток, и проблему отчётности.

Обучение до 03.03.2025. Для классификатора исходные даты только до 24.02.2025: весь 7-дневный целевой интервал укладывается в обучение. Валидация 04–17 марта. Прогнозы выдаются двумя неперекрывающимися неделями. Новые факты первой недели доступны второй как история, но модели не переобучаются.

Дополнительная ранняя диагностика: обучение до 17.02, 739 организаций, проверка двух следующих недель. Общий порог выбранной архитектуры дал precision 42,86%, recall 8,76%. Это не независимая оценка выбора и не тот же охват, что основное сравнение. Недельные и групповые метрики находятся в отчёте и интерфейсе.

## Фронтенд

Сохранены новые бренд, цвета и компоненты напарника. Обновлена страница метрик: до/после, экспериментальные варианты, матрица ошибок, недели/группы, исходные данные, версия и хеш модели. Убрано утверждение о независимом тесте.

Главная ведёт к предупреждениям. В карточке отделены риск и численный прогноз, исправлено отрицательное «+число» в ленте. Из шапки убрано неподтверждённое обозначение принадлежности Минздраву. Навигация доступна на небольшом экране.

Существующая карта сохранена как отдельная историческая аналитика. Ноль больше не означает отсутствие данных, постоянный зелёный индикатор API заменён реальным состоянием загрузки. Экран явно сообщает, что его общий прогноз относится к основному авторизованному API, а не к модели пилота. Полная интеграция обученных моделей в операционный API с Keycloak в эту итерацию не входит; пилот — отдельный локальный контур.

## Воспроизведение

Из корня проекта, в подготовленном Python-окружении:

```sh
docker compose -f docker-compose.pilot.yml stop pilot-api
.venv/bin/python -m ml.source_audit
.venv/bin/python -m ml.improve
.venv/bin/python -m pilot.verify
.venv/bin/python -m pytest tests/monitoring -q
docker compose -f docker-compose.pilot.yml up -d --build
docker compose -f docker-compose.pilot.yml restart pilot-api
```

Для первого запуска скачать открытые CSV командой `python3 -m pilot.download`. `ml.improve` при отсутствии v1 обучит базовую версию в data/monitoring-v1. При наличии проверит контрольные суммы исходных файлов, чтобы сравнение не смешало разные выгрузки. Повторное обучение не должно идти одновременно с обслуживанием API: остановить API на время публикации артефакта, затем запустить.

В data/monitoring-v1 сохранены модель и показатели до изменений; в data/monitoring — выбранная модель, отчёт, аудит и результаты воспроизведения. В Git эти файлы не попадают. Публичный агрегированный отчёт без строк пациентов: docs/ml/MONITORING_V2_RESULTS.json. В нём сохранены параметры и неудачные варианты. Точное обучение воспроизводится из кода и файлов с указанными SHA-256.

`pilot.verify` загружает сохранённую модель, пересчитывает все 15 дат воспроизведения, сверяет набор предупреждений, прогнозы и TP/FP/FN/TN с отчётом. Метрики сайта приходят из того же bundle, по которому работает сервер.
