# MedSignal: рабочий локальный пилот

Это также отдельный исторический исследовательский local pilot; он не является operational мониторингом.

Пилот отвечает на один вопрос: **по какой организации исходной выгрузки ожидается рост числа направлений на следующей исторической неделе?** Это прогноз входящего потока, не диагноз, не измерение очереди и не доказанная перегрузка.

В основе — существующий Next.js сайт и отдельный модуль обучаемой модели в `ml/monitoring.py`. Локальный API `pilot/api.py` загружает сохранённую модель и на каждом новом историческом дне заново выполняет предсказание. Рабочий API с Keycloak не изменён и не используется этим режимом. Пилот содержит только агрегаты открытой выгрузки и слушает `127.0.0.1:8088`.

## Статус и граница допуска — 23.09.2026

Это историческое воспроизведение, не текущий мониторинг больниц. Идентичность
организации источника не равна подтверждённой canonical Hospital: без mappings
результат остаётся исследовательским и не превращается в hospital/global signal.
Основной продукт использует Keycloak/OIDC, scopes, PostgreSQL и Audit Log;
`replay-state.json` не является production persistence. Основной Phase 5A выбрал
`weekly_naive`, а описанная ниже обучаемая модель относится только к local pilot.

Для допуска нужны новые данные после уже просмотренного test, утверждённая
политика precision/recall, false-alert budget и числа независимых эпизодов.
Без политики — `POLICY_NOT_APPROVED`, без новых данных — `INSUFFICIENT_DATA`.
Пороговая политика 20% / 35% / 50% не подгоняется по test. TLS, corporate SSO и
production E2E не подтверждаются запуском этого режима или прежним acceptance.

Waiting содержит один срез: разброс дат регистрации не подтверждает историю
очереди. Для refusal ratio нужен согласованный знаменатель и общая популяция.
Подробности: [semantic correction](data/TARGET_FEASIBILITY.md),
[roadmap](ROADMAP.md), [дизайн консолидации](superpowers/specs/2026-09-23-pilot-consolidation-design.md).

## Что показывать

1. Открыть http://localhost:8088 — главная ведёт в ленту предупреждений.
2. Нажать «День»: добавляется следующий исторический день, модель получает только доступную к нему историю, пересчитывает прогноз и список сигналов.
3. «Запустить» включает обновление каждые 10 секунд; на конце выгрузки воспроизведение останавливается. Никакие новые записи не генерируются.
4. Открыть предупреждение: организация, критичность, основания, прогноз на 7 дней, план действий с ответственными и качество прогноза этой больницы.
5. Изменить статус на «В работе» — он сохраняется после обновления страницы и перезапуска. Новая дата — новое предупреждение; это пока не группировка нескольких дней в один инцидент.
6. Открыть «Обучение и проверка»: источник, даты разделения данных, ошибки модели и простых методов, результат проверки самих предупреждений, хеш сохранённой модели.

## Обучение — настоящее

Из трёх CSV прочитаны 767 130 записей за 01.01–31.03.2025. Для модели используются принимающая организация и дата регистрации. Диагнозы, исход госпитализации, код пациента и последующие события не являются признаками. Прогнозируется число записей, не число уникальных пациентов.

Из записей строятся дневные ряды по организациям. В обучение допускаются организации с ≥100 записями и ≥28 активными днями именно в обучающем периоде. Нельзя выбирать организации по их будущему поведению.

Обучается общая для организаций модель градиентного бустинга `HistGradientBoostingRegressor` с Poisson loss. Она учит зависимость будущего числа направлений от лагов, средних за 7/14/28 дней, дня недели и горизонта. На каждую из следующих семи дат — прямое предсказание. Это не LLM и не набор прописанных ответов.

- Обучение: 01.01–03.03.2025.
- Проверка: 04.03–17.03.2025. Здесь выбирается простой метод сравнения и оценивается качество по организациям.
- Финальный тест: 18.03–31.03.2025, две неперекрывающиеся недели. Модель заморожена; факты первой недели доступны как входная история второй, но не для обучения.
- 837 организаций, 181 629 обучающих примеров.

На финальном тесте MAE модели — **6,305 направления на организацию в день**, повторения прошлой недели — **7,906**. WAPE модели — **84,286%**, простого прогноза — **105,690%**. Средняя ошибка меньше примерно на 20%, но относительная ошибка велика. Особенно плохо прогнозируется неделя резкого падения потока. Причина падения из этих данных не установлена.

## Важный результат проверки предупреждений

Порог: прогнозируемая неделя ≥120% среднего недельного потока за предшествующие 28 дней, прирост ≥10 направлений, базовый поток ≥20. Критичность: +20% / +35% / +50%. Это явная политика пилота поверх прогноза обученной модели; она не обучалась и не является медицинским нормативом.

На двух тестовых неделях: 14 предупреждений, из них 6 подтверждённых эпизодов роста, 8 ложных; 142 эпизода роста пропущено. Точность предупреждений 42,86%, полнота 4,05%. **Модель обучается и предсказывает, но надёжная система обнаружения рисков пока не получилась.** Результат не скрывается, предупреждение об этом есть в интерфейсе. Проверяется рост направлений, не перегрузка.

Предлагаемые действия — прозрачные правила реагирования. Модель не обучена выбирать управленческое решение: в исходных данных нет истории действий и результатов. Эффект на очередь не придумывается.

## Запуск и повторяемая проверка

Из корня проекта:

```sh
python3 -m pilot.download
mkdir -p data/monitoring
docker compose -f docker-compose.pilot.yml build
docker compose -f docker-compose.pilot.yml run --rm train
docker compose -f docker-compose.pilot.yml up -d
```

После нового обучения перезапустить API, чтобы он загрузил новый артефакт:

```sh
docker compose -f docker-compose.pilot.yml restart pilot-api
```

В уже подготовленном локальном окружении:

```sh
.venv/bin/python -m ml.monitoring
.venv/bin/python -m pilot.verify
.venv/bin/python -m pytest tests/monitoring -q
cd frontend
npm run typecheck
npm run lint
npm run build
```

`pilot.verify` загружает настоящий сохранённый estimator, сверяет SHA-256 и повторно вычисляет прогнозы для 1 674 сочетаний больница/дата. Проверяется совпадение прогнозов и набора предупреждений с результатом обучения.

Тесты проверяют отсутствие использования будущего в признаках и обучении, зависимость обученной модели от целевых данных, защиту от дублирования файлов и неполной выгрузки, порог предупреждения, конец воспроизведения, сохранение статуса и отсутствие выдуманных результатов при отсутствии модели.

Артефакты в `data/monitoring/`: `model.joblib`, `report.json`, `bundle.json`, `replay-state.json`. В Git не попадают ни исходные медицинские выгрузки, ни артефакты. Сервер загружает только локально созданный и сверенный по хешу файл модели; не принимать чужие joblib-файлы через загрузку.

## Что необходимо до реального использования

- Увеличить историю и получить проверенные календарные/организационные факторы; отдельно исследовать неполноту выгрузок и резкие изменения потока.
- На более длинной истории обучить и проверить модель обнаружения эпизодов роста, повышая полноту без неприемлемого числа ложных тревог. Для новых итераций нужен новый нетронутый тестовый период.
- Получить ежедневные снимки очереди, вместимость по профилям и подтверждённые соответствия кодов организаций. Тогда проверять именно перегрузку и ожидание.
- Получить источник регулярных поставок/API. Сейчас работает честное воспроизведение, а не интеграция с больницами. При подключении: приём → проверка полноты/дедупликация → дневные агрегаты → inference → сохранение предупреждений. Переобучение отдельной проверяемой задачей, а не после каждого запроса.
- Перенести локальный сценарий в существующие авторизованные сервисы, добавить объединение повторных сигналов в инцидент, журнал действий и мониторинг качества. Публично локальный пилот не публиковать.

Полный базовый стек на этой машине не запущен: Docker не смог получить закреплённый образ MinIO. Пилот использует отдельный compose и от этого хранилища не зависит. Карта Казахстана и графики в текущую итерацию не входят.
