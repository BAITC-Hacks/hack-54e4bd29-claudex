# ROADMAP — план развития

Три горизонта: MVP для демонстрации полного цикла, Pilot для проверки на реальных данных с реальными пользователями, Production для эксплуатации.

## 1. MVP

Цель — показать связный путь от данных до решения человека и обратно к контролю. Полнота функций уступает связности пути.

### Фазы

| Фаза | Содержание | Результат |
|---|---|---|
| 0 | Архитектура, документация, границы, ADR | Согласованная основа. **Завершена** |
| 1 | Docker Compose, скелеты backend и frontend, хранилища, аутентификация Keycloak, проверки здоровья, журналирование, конфигурация, CI | Система запускается воспроизводимо. **Завершена** |
| 2 | Доменные сущности, RBAC, область данных, аудит | Данные защищены и прослеживаемы с самого начала |
| 3 | Импорт, валидация, очистка, псевдонимизация, загрузка в ClickHouse, отчёт качества | Данные внутри системы |
| 4 | Situation Center, метрики организаций, исторические графики, сравнение | Пользователь видит ситуацию |
| 5 | Data Audit, выбор цели, baseline, признаки, модель, оценка, MLflow, инференс, SHAP | Проверяемый прогноз с известной ошибкой |
| 6 | Signal Engine: правила, статистика, ML; лента, карточка, объяснение, Risk Score | Система предупреждает и объясняет |
| 7 | What-if симулятор, сравнение базового и расчётного сценария | Проверка решения до его принятия |
| 8 | Обзор безопасности, ограничение частоты, усиление конфигурации | Готовность к работе с чувствительными данными |
| 9 | Интеграционные, E2E, нагрузочные тесты и тесты безопасности | Подтверждённое качество |
| 10 | Сквозной демонстрационный сценарий | Готовность к показу |

### Критическая зависимость

PHASE 5 не начинается без Data Audit. Если структура данных не позволяет выбрать проверяемую цель, ML-часть сокращается до статистических методов, а PHASE 6 реализуется на двух источниках сигналов из трёх. Это заранее предусмотренный, а не аварийный сценарий: система остаётся полезной без прогноза ([ADR-0007](ADR/0007-data-audit-before-ml-target.md)).

### Признаки завершения

Полный перечень — в разделе Definition of Done исходного задания. Ключевое: воспроизводимый запуск, работающий RBAC, проверяемый прогноз с метрикой ошибки, объяснённый сигнал, сравнение сценариев, запись решения в аудит, отсутствие секретов и персональных данных в репозитории.

## 2. Pilot

Цель — проверить систему на реальных данных и реальных пользователях в ограниченном контуре.

| Направление | Содержание |
|---|---|
| Данные | Регулярная выгрузка вместо разовой загрузки, согласованный регламент обновления, сопоставление справочников организаций |
| Аутентификация | Отдельная область Keycloak для пилота, реальные пользователи, единый вход, при необходимости многофакторность |
| Качество модели | Накопление фактических значений, сравнение прогноза с фактом, регулярное переобучение |
| Сигналы | Настройка порогов по обратной связи пользователей, снижение доли ложных срабатываний |
| Сценарии | Расширение набора: изменение мощности, изменение сроков ожидания |
| Наблюдаемость | Полноценные панели Grafana, оповещения, мониторинг дрейфа |
| Обратная связь | Оценка полезности сигнала пользователем как входной сигнал для настройки правил |
| Эксплуатация | Резервное копирование с проверкой восстановления, регламент инцидентов |

Главный вопрос пилота — не точность модели, а доля сигналов, приведших к действию. Система, генерирующая верные, но игнорируемые предупреждения, не решает задачу.

## 3. Production

| Направление | Содержание |
|---|---|
| Масштабирование | Несколько экземпляров приложения, разделение очередей, реплика для чтения |
| Инфраструктура | При необходимости — Kubernetes, автоматическое масштабирование |
| Интеграции | Прямое подключение к источникам вместо файловых выгрузок |
| Безопасность | Внешняя оценка защищённости, аттестация при необходимости, полный контур управления секретами |
| Модели | Автоматическое переобучение по расписанию, контроль деградации, откат версии |
| Расширение функций | Пункты из раздела «за пределами MVP» по мере подтверждения данных |
| Регламенты | Сроки хранения, порядок доступа, процедуры реагирования |

## 4. Отложенные функции и условия их включения

| Функция | Условие включения |
|---|---|
| Прогноз даты выписки | Доступ к клиническим данным и отдельная правовая оценка |
| Прогноз освобождения койки | Данные о коечном фонде в реальном времени |
| Эпидемиологическое прогнозирование | Внешние эпидданные и согласованная методология |
| Финансовый эффект сценария | Тарифная модель и данные оплаты |
| Автоматическое перенаправление | Только как исполнение утверждённого человеком решения |
| Сложная корреляция инцидентов | Накопленная статистика совместных срабатываний |
| Мобильный интерфейс | Подтверждённый спрос от пользователей пилота |

## 5. Технический долг, принятый осознанно

| Долг | Причина | Срок возврата |
|---|---|---|
| Область данных не разрешается: у ролей без глобальной области она пуста | Таблица областей появляется вместе с доменом | PHASE 2 |
| Вход через браузер не реализован: токен получают служебным клиентом | Фундамент проверяется без UI входа | PHASE 2 |
| Простая группировка инцидентов | Нет статистики для сложной корреляции | Pilot |
| Один тип сценария симуляции | Достаточно для проверки цикла | Pilot |
| Статистические методы вместо обучаемых для аномалий | Интерпретируемость и короткие ряды | По результатам пилота |
| Ручное сопоставление справочников организаций | Нет подтверждённого общего кода | Pilot |
| Отсутствие автоматического переобучения | Нет регулярного потока данных | Pilot |

Долг зафиксирован явно, чтобы не превратиться в неявное свойство системы.

## 6. Основные риски

| Риск | Влияние | Реакция |
|---|---|---|
| Структура данных не позволяет выбрать цель | ML-часть сокращается | Система работает на правилах и статистике |
| Недостаточная глубина истории | Прогноз невозможен для части организаций | Явный отказ от прогноза вместо недостоверного |
| Нерегулярное обновление данных | Сигналы теряют смысл | `DATA_STALE` как самостоятельный сигнал |
| Несопоставимость справочников организаций | Невозможность связать источники | Явная таблица соответствия |
| Высокая доля ложных срабатываний | Потеря доверия пользователей | Минимальная длительность условия, дедупликация, настройка порогов |
| Восприятие расчёта как указания | Неверные решения | Обязательные дисклеймеры с сервера, формулировка «расчётный сценарий» |
| Обнаружение персональных данных в выгрузках | Правовой риск | Отсечение на входе, строгий режим, требование к источнику |
| Размывание архитектурных границ под сроком | Потеря управляемости кода | Автоматическая проверка границ в CI, 9 контрактов |
